# Axiom Runtime v4.0.0 全面技术报告

> 从碎片化多智能体系统到认知运行时 —— 10 项架构改进 + 7 项核心缺陷修复 + 扩展至 150 MCP 工具

---

## 1. 项目概述

Axiom 是一个**认知运行时 (Cognitive Runtime)**，面向 RTX 3050 Ti 4GB VRAM 等消费级 GPU 的本地 AI 开发辅助系统。它从碎片化的多智能体系统升级统一为三层认知架构：

| 层级 | 功能 | 核心模块 |
|------|------|----------|
| **Tier 1** 数据摄取 | Web 爬取、文档解析、知识图谱填充 | `crawl/`, `kg/` |
| **Tier 2** 推理与存储 | 确定性推理、意识流、心智模型、约束求解 | `dre/`, `kal/` |
| **Tier 3** 代理与接口 | MCP 协议服务、场景路由、工具注册、执行模式 | `mcp/`, `agents/` |

### 1.1 关键设计原则

| 原则 | 说明 | 落地文件 |
|------|------|----------|
| 确定性优先 | 零 LLM 依赖的确定性操作 (AST 解析、场景路由、约束求解) | `markdown-ast.ts`, `scene-router.ts`, `solver.ts` |
| 三级降级 | 本地 LLM → 云 API → 规则引擎的降级链 | `engine.ts:202-250` |
| 统一知识访问 | 通过 `node_id` 系统跨 Vault/KG/DRE 三存储统一查询 | `knowledge-access-layer.ts`, `node-id.ts` |
| 分层测试 | 模块级测试 (55 cognitive tests) + 场景级测试 (13 scene tests) | `cognitive-modules.test.ts`, `scene-router.test.ts` |

### 2.2 Tier 2: 推理与存储

#### 2.2.1 `src/dre/engine.ts` — DREngine (525 行)

**目的**: 确定性推理引擎顶层编排器。初始化所有子系统 (VFS, SQLite, KnowledgeStore, Pipeline, KG, LLM, Consciousness, MentalModelPool, ReasoningGraph, ConstraintSolver, ActorSystem)。

**核心方法**:
| 方法 | 说明 |
|------|------|
| `writeKnowledge()` | 写入知识 → Pipeline 验证 → KnowledgeStore 持久化 |
| `readKnowledge()` | 从 KnowledgeStore 读取 |
| `searchKnowledge()` | 跨 KnowledgeStore 搜索 |
| `subgraph()` | BFS 子图检索 |
| `consciousnessStep()` | 三级降级链: 本地 LLM → 云 API → 规则引擎 |
| `close()` | 异步关闭 ActorSystem, 清理资源 |

**三级降级链** (`dre_consciousness_step`):
```
本地 LLM (llama.cpp) ──失败──→ 云 API (OpenAI-compatible) ──失败──→ 规则引擎 (字符串匹配)
   ↑ canRunLocal() 判断          ↑ cloudFallback 配置                 ↑ 保底响应
```

**测试效果**: `consciousness.test.ts` 通过, 降级链在 VRAM 不足时自动触发。

#### 2.2.2 `src/dre/storage/knowledge-store.ts` (746 行)

**目的**: 完整知识 CRUD 层, 支持 7 种知识范式, 版本快照, 实体关系图谱。

| 类 | 方法数 | 说明 |
|----|--------|------|
| `KnowledgeStore` | 10 | 读写/搜索/版本/边操作/子图 |
| `BehaviorKnowledge` | 2 | 从规则节点提取行为模式 |
| `ProcedureKnowledge` | 3 | 步骤解析/验证/下一步预测 |
| `HypothesisManager` | 3 | 假设提出/证据积累/状态机 |

**7 种知识范式**:
```
fact | rule | procedure | concept | behavior | prediction | hypothesis
```

**行为知识提取** (`BehaviorKnowledge.extractFromRule`):
- 解析 `IF condition THEN conclusion` 格式的规则节点
- 返回 `Behavior { triggers, outcomes, preconditions, sideEffects }`
- `predict()` 检查前置条件 → 返回最高概率结果

**过程性知识** (`ProcedureKnowledge.parseFromContent`):
- 解析编号步骤 + `IF/THEN/ELSE` 分支
- `validate()` 检查缺失描述/条件
- `getNextStep()` 评估条件分支, 支持 `&&`/`||` 递归

**假设管理器** (`HypothesisManager`):
- 5 状态生命周期: `untested → testing → confirmed/refuted/inconclusive`
- 证据积累 → 自动状态转换 (≥3 证据自动判定)
- 置信度计算: `supporting / (supporting + contradicting)`

**测试效果**: 55 个认知模块测试全部通过, 含 SQLite 集成的 HypothesisManager 全生命周期测试。

#### 2.2.3 `src/dre/pipeline/pipeline.ts` (348 行)

**目的**: 三阶段知识验证管道。

| 阶段 | 条件 | 操作 |
|------|------|------|
| Stage 0 | 风险 < 0.3 | 直接接受 + 写入 |
| Stage 2 | 0.3 ≤ 风险 < 0.7 | Web 验证 (占位) |
| Stage 3 | 风险 ≥ 0.7 | LLM 自推理 + JSON Schema 约束 |

**规则引擎**: `BlacklistRule` (关键词, 0.3), `LengthRule` (长度, 0.2), `SourceTypeRule` (LLM 来源, 0.1)。

#### 2.2.4 `src/dre/consciousness/stream.ts` (458 行)

**目的**: 三层记忆架构 + 事件驱动意识流。

| 组件 | 容量 | 淘汰策略 |
|------|------|----------|
| `WorkingMemory` | FIFO, 默认 10 | 队首淘汰 |
| `EpisodicMemory` | TTL 3600s | 清理过期条目 |
| `ReflectionQueue` | 5 触发条件 | 连续失败/输出不一致/置信度方差 |

**事件驱动循环**:
```
observe → memory → decide → trace → reflect
                                 └→ emit "reflection" 事件
```

### 2.3 Tier 2: 认知模块

#### 2.3.1 `MentalModelPool` (心智模型池)

| 文件 | `src/dre/mental-model/pool.ts` | 行数 332 |
|------|-------------------------------|----------|

**目的**: 构建内部仿真模型 (概念图 + 状态转换 + 预测), 桥接模式识别到技能推荐。

**核心接口**:
| 接口 | 字段 |
|------|------|
| `MentalModel` | `concepts[]`, `transitions[]`, `initialState`, `currentState`, `confidence`, `usageCount` |
| `ModelConcept` | `id`, `name`, `description`, `properties`, `relations[]` |
| `StateTransition` | `from`, `to`, `trigger`, `requiredConcepts[]`, `probability` |
| `ModelPattern` | `conceptChain[]`, `statePath[]`, `confidence`, `suggestedSkill` |

**关键技术点**:
- **关系扩展匹配**: `matchPattern()` 除直接概念匹配外, 还沿 `may-cause`/`requires` 关系扩展
- **深拷贝注册**: `register()` 使用 `JSON.parse(JSON.stringify())` 防止共享可变状态
- **BFS 状态路径**: `findStatePath()` 使用广度优先搜索从当前状态到目标状态

**预注册模型**:
| 模型 | 状态链 |
|------|--------|
| Git 冲突解决 | `clean→merging→conflict→resolved→clean` |
| 代码重构 | `smelly→analyzing→testing→refactoring→verifying→clean` |

**测试效果**: 13 个测试全部通过, 含关系扩展匹配和 BFS 路径测试。

#### 2.3.2 `ReasoningGraph` (推理图)

| 文件 | `src/dre/reasoning/graph.ts` | 行数 477 |
|------|------------------------------|----------|

**目的**: 用图结构取代单次 LLM 调用, 分解推理为: 建图 → 检测缺口 → LLM 填充缺口 → 验证。

**节点类型**: `premise | inference | conclusion | evidence | gap`

**边关系**: `supports | contradicts | implies | requires | explains`

**缺口检测器** (4 种):
| 检测器 | 条件 | 优先级 |
|--------|------|--------|
| 孤立前提 | 前提无推理边 | high |
| 无支撑结论 | 结论无入边 | high |
| 弱连接 | 边置信度 < 0.5 | medium |
| 断开链 | 图分裂为不连通组件 | medium |

**LLM 精确填充**:
- `fillGapFromObject()`: 接收 LLM 响应 → 创建推理节点 → 自动链接到相关节点
- `generateGapFillingPrompt()`: 生成精确的 LLM 填充提示模板

**测试效果**: 14 个测试全部通过, 含 `fillGapFromObject`/`fillGap`/`fillGap(nonExistentId)` 边界测试。

#### 2.3.3 `ConstraintSolver` (约束求解器)

| 文件 | `src/dre/constraint/solver.ts` | 行数 586 |
|------|-------------------------------|----------|

**目的**: 五维约束求解, 安全动作选择。

**五个维度**:
| 维度 | 评估器逻辑 | 示例 |
|------|-----------|------|
| `logical` | 检查上下文标志 | requires/prohibits/conflicts |
| `physical` | 数值比较 | min_value/max_value/between |
| `semantic` | 属性匹配 | equals/not_equals/in_set |
| `policy` | 环境级检查 | not_equals (生产环境禁删除) |
| `temporal` | 时间范围 | between (工作时段 9-18) |

**12 种约束类型**: `requires | prohibits | enables | conflicts | excludes | min_value | max_value | equals | not_equals | in_set | not_in_set | between`

**预注册约束**:
| 集合 | 内容 | 默认启用 |
|------|------|----------|
| GPU_CONSTRAINTS | VRAM ≥ 500MB (通用), ≥ 1100MB (Qwen3) | ✔ |
| POLICY_CONSTRAINTS | 生产环境禁 delete/experimental | ✔ |
| TEMPORAL_CONSTRAINTS | 工作时间 9-18 | ✘ |

**测试效果**: 11 个测试全部通过, 含 GPU 预算检查、生产策略、候选排序。

#### 2.3.4 `ActorSystem` (Actor 系统)

| 文件 | `src/dre/actor/system.ts` | 行数 473 |
|------|---------------------------|----------|

**目的**: 轻量 Actor 模型, 每个认知模块包装为一个 Actor, 通过消息通信。

**消息类型**: `query | response | update | notify | request | ack | error`

**Actor 生命周期**:
```
register(behavior) ─→ init() ─→ processNext() ─→ destroy()
                                    ↑
                                mailbox (queue)
```

**4 个预注册 Actor**:
| Actor | ID | 处理主题 | 委托模块 |
|-------|----|---------|----------|
| KnowledgeActor | `knowledge` | query/validate | KAL |
| ConstraintActor | `constraint` | check/suggest | ConstraintSolver |
| MentalModelActor | `mental-model` | match/predict | MentalModelPool |
| ReasoningActor | `reasoning` | build/detect-gaps | ReasoningGraph |

**关键技术点**:
- `queryState`: request/response 模式, 5 秒超时, `resolved` 标志防止竞态条件
- `ActorInstance` 继承 `EventEmitter`, 单线程邮箱处理
- `createDefaultActorSystem()`: 一次注册全部 4 个 Actor

**测试效果**: 5 个测试全部通过, 含竞态条件安全测试。

## 8. 技术要点总结

### 8.1 确定性优先原则

| 操作 | LLM 依赖 | 确定性替代 |
|------|----------|-----------|
| Markdown 解析 | 传统需要 LLM | 正则引擎 (`markdown-ast.ts`) |
| 场景路由 | 传统需要 LLM | 关键词匹配 (`scene-router.ts`) |
| 约束求解 | 传统需要 LLM | 规则引擎 (`solver.ts`) |
| 概念匹配 | 传统需要 embedding | 关系图+状态 BFS (`pool.ts`) |
| 知识写入 | 混合 | 确定性规则+LLM 验证 (`pipeline.ts`) |

### 8.2 三级降级架构

```
                        ┌──────────────┐
                        │  本地 LLM     │  ← llama.cpp / Qwen3-1.7B
                        │  (primary)   │     约 1.1GB VRAM
                        └──────┬───────┘
                               │ 失败
                               ▼
                        ┌──────────────┐
                        │  云 API       │  ← OpenAI-compatible
                        │  (secondary)  │     需配置 baseUrl+apiKey
                        └──────┬───────┘
                               │ 失败
                               ▼
                        ┌──────────────┐
                        │  规则引擎     │  ← 保底字符串匹配
                        │  (fallback)   │     永不失败
                        └──────────────┘
```
